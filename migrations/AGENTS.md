# migrations/AGENTS.md

> Conventions for SQL migration files in this project. Read this BEFORE writing or editing any
> migration. Sub-context of root AGENTS.md.

## Naming

- `NNN_<description>.sql` — 3-digit prefix orders the migration
- Use underscores, not dashes: `105_seed_admin_regions.sql` (wrangler sorts alphabetically)
- `100_drop_all.sql` is reserved for the destructive drop (currently unused; v2 uses fresh D1)
- `cities/<cca2>.sql` — generated per-country city seed (gitignored, regenerable)

## Format

```sql
-- Migration NNN: <one-line description>
-- Source: <where the data comes from>
-- Generated by: <script that produced this file>

INSERT INTO <table> (<col1>, <col2>, ...)
VALUES
  (1, 'foo', ...),
  (2, 'bar', ...),
  (3, 'baz', ...);
```

- Comments at top: what, source, generator
- One INSERT statement per migration file (or per logical group)
- Multi-row VALUES, semicolon only at the end

## D1 limits (binding)

| Limit | Value | Safe target |
|---|---|---|
| Variables per prepared statement | ~100 | ≤ 95 |
| Statement size | ~1MB | ≤ 800KB |
| Total DB size | 10GB | (no current concern) |
| Tables per DB | 10,000 | (no current concern) |

**BATCH size by column count (always under 95 vars):**

| Cols | BATCH | Vars |
|---|---|---|
| 4-5 | 20+ | 80-100 |
| 6 | 16 | 96 |
| 7 | 14 | 98 |
| 8 | 12 | 96 |
| 9 | 11 | 99 |
| 10 | 9-10 | 90-100 |
| 11 | 9 | 99 |
| 12 | 8 | 96 |
| 14 | 7 | 98 |
| 15 | 4-6 | 60-90 |

**For multi-row INSERTs:** split into separate INSERT statements (each with own `;`), each
holding BATCH rows. NEVER put `;` inside one INSERT.

## NULL handling

**Always use `IS NULL` checks, never `or`:**

```sql
-- CORRECT
CASE WHEN col IS NULL THEN 'NULL' ELSE col END

-- WRONG (turns 0 into 'NULL' because 0 is falsy)
CASE WHEN col OR 'NULL' THEN 'NULL' ELSE col END
```

**Pattern for Python generators:**

```python
def sql_num(v):
    if v is None: return 'NULL'
    if isinstance(v, bool): return '1' if v else '0'
    return str(v)
```

## Destructive changes (binding — never without user OK)

- `DROP TABLE` — requires user explicit "do it" + new D1 backup
- `DROP DATABASE` — NEVER (use new D1 approach instead)
- `DROP COLUMN` — SQLite supports it but check downstream queries first
- `ALTER TABLE ... DROP NOT NULL` — NOT supported in D1. Drop+recreate the table.

## Current known issue

**Cities FK constraint failure (in progress):**

A city's `country_id` or `state_id` references a row that doesn't exist in `countries` or
`administrative_regions`. The `countries+states+cities.json` source has different state_ids
than the standalone `country+states.json` used to generate migration 105.

**Diagnostic queries:**

```sql
-- Find orphan state_ids in cities (after first N countries applied)
SELECT DISTINCT c.state_id
FROM cities c
LEFT JOIN administrative_regions a ON a.id = c.state_id
WHERE a.id IS NULL AND c.state_id IS NOT NULL
LIMIT 50;

-- Find orphan country_ids (should be 0)
SELECT DISTINCT c.country_id
FROM cities c
LEFT JOIN countries co ON co.id = c.country_id
WHERE co.id IS NULL;
```

**Likely fix:** relax the FK to ON DELETE SET NULL or use a recovery migration that NULLs
out the orphan state_ids before continuing the apply.

## Common gotchas

- D1 file upload limit ~1MB. For larger files, split into multiple statements.
- D1 does not support `ALTER TABLE ... ADD CONSTRAINT`. Add constraints in the CREATE TABLE.
- D1 does not support `ALTER TABLE ... DROP NOT NULL`. Recreate the table.
- SQLite's `LIKE` is case-insensitive by default for ASCII; for Unicode, use `COLLATE NOCASE`.
- Foreign keys are OFF by default in SQLite. D1 enables them per-connection.

## Testing a migration locally

```bash
# Spin up a local D1 (SQLite)
npm run dev:remote
# This binds to the real D1, not local

# Or for offline testing:
npx wrangler d1 execute <db> --local --file=migrations/<your>.sql
# Note: --local uses local SQLite, no D1-specific features
```

## Adding a new migration (checklist)

1. Pick a 3-digit prefix that doesn't collide with existing files
2. Write the SQL following the format above
3. Update the verify command in the doc above
4. If it adds a new column, update `src/lib/types.ts` and the DAO
5. If it adds a new table, update `src/lib/db.ts` (DAOs) and `src/lib/schemas.ts` (Zod)
6. Update `src/routes/health.ts` and `src/routes/status.ts` if the new table is in DB stats
7. Run `npm run sync:readme` to update auto-generated sections
8. Commit on a `feature/*` branch with a clear message
9. Push and ask user to verify
