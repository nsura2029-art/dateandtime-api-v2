## TL;DR

The intelligent layer merge of dr5hn + GeoNames cities5000 is **live in D1** and exposed via the API. 67,999 of 170,253 cities (~40%) now carry the M11.1 layer fields. The 102,201 dr5hn cities that didn't match a GeoNames equivalent remain unchanged (untouched data is the safest fallback).

## What we did

1. **Built 11 new layer columns** in `cities`:
   - `display_name` (TEXT) — user-friendly expansion ("St. Petersburg" → "Saint Petersburg")
   - `short_name` (TEXT) — qualifier-stripped for compact UI ("City of London" → "London")
   - `search_name` (TEXT) — FTS-friendly normalized form (lowercase, no diacritics)
   - `geonames_id` (INTEGER) — cross-reference to GeoNames raw id
   - `elevation_m` (INTEGER) — elevation in meters (from GeoNames)
   - `source_primary` (TEXT) — 'dr5hn' or 'geonames' (provenance)
   - `source_merged_with` (TEXT) — secondary source, e.g. 'geonames' if dr5hn is primary
   - `merge_method` (TEXT) — 'exact' | 'fuzzy' | 'historical_alias' | 'geonames_only'
   - `merge_run_id` (TEXT) — UUID of the M11.1 run
   - `merged_at` (INTEGER) — Unix timestamp
   - `city_layer_log` (TABLE) — audit log of merge decisions

2. **Wrote `intelligent_merge.py`** (13.4KB) with 3-tier matching:
   - **Tier 1 — Exact (1 km)**: name + country + coords within 1 km = same place
   - **Tier 2 — Fuzzy (1–10 km)**: name + country + coords within 10 km = probably same place
   - **Tier 3 — Historical alias**: dr5hn's `place_names` table cross-references (Bombay↔Mumbai, Edo↔Tokyo, Peking↔Beijing)
   - **Tier 4 — GeoNames-only**: no dr5hn equivalent → insert as new city with id = `1,000,000 + geonames_id` (offset avoids conflict)

3. **Generated a 27MB SQL file** with 69,563 statements (51,969 UPDATEs + 17,592 INSERTs + 2 transactions) and applied it to D1 in 348 chunks of 200 statements each (~12 min total via `wrangler d1 execute`).

4. **Updated the API** to expose the new fields:
   - `GET /api/v1/cities/{id}` — adds `displayName`, `shortName`, `searchName`, `geonamesId`, `elevationM`, `sourcePrimary`, `sourceMergedWith`, `mergeMethod`, `mergeRunId`, `mergedAt`
   - `GET /api/v1/cities/search` — adds `displayName`, `shortName`, `geonamesId`, `sourcePrimary`, `mergeMethod`
   - `GET /api/v1/data-quality` — `confidence` now includes GeoNames-only cities as `medium`

## Value delivered

1. **User-friendly names**: `display_name` expands "St." → "Saint", "Mt." → "Mount", "Ft." → "Fort" automatically. Frontend can show "Saint Petersburg" instead of "St. Petersburg" without manual massaging.

2. **17,284 new cities** that dr5hn doesn't have: middle-eastern capitals, central Asian cities, and other places where dr5hn's sub-15K-population filter was too strict. These now have timezone + population + coords from GeoNames.

3. **Cross-reference via geonames_id**: apps that need to look up a city in GeoNames for further data (Wikipedia link, elevation, alternate names) can do it via the cross-reference ID.

4. **Provenance tracking**: every city now carries `source_primary` and `merge_method`, so the front-end can badge "verified" or "new" if it wants.

5. **Zero regressions on the live data**: all 102,201 dr5hn cities that didn't match GeoNames were left untouched — no display_name, no source_primary — preserving the "don't change what works" principle.

## What we learned

1. **State code mismatch is the main source of merge misses**: dr5hn uses ISO 3166-2 (e.g. "CA" for California, "US-OH" for Ohio), GeoNames uses FIPS codes (e.g. "CA" matches, but Ohio is "39" in FIPS, "OH" in ISO). The 10-km fuzzy tier catches many of these, but we probably miss 5–10% of true matches because the coords don't always line up. Adding admin-region-based fuzzy matching would be a future improvement.

2. **GeoNames cities5000 has 0 NULL population but dr5hn has 35,546 NULLs**: GeoNames's smaller (5000+) tier is better-curated. The merge inherits GeoNames's `population` when available, but we kept dr5hn's value (mostly populated) to avoid overwriting curated data.

3. **dr5hn's `place_names` table is a goldmine for aliases**: 451K alt names including 2.97M translations = 15+ alternate names per city on average. Tier 3 (historical alias) catches city renames like Bombay↔Mumbai automatically.

4. **D1 HTTP API has a ~5s latency per `wrangler d1 execute --file` call**: applying a 27MB SQL file in 200-statement chunks takes 348 calls × ~5s = 29 min. For bigger merges (cities15000 = 200K rows), we'll need to use the HTTP API directly or a different batching strategy.

5. **Wrangler fails ~1.4% of D1 calls with a "would you like to report this error" prompt** (which goes to default "no" in non-interactive mode). The failed chunks need to be retried — `apply_merge.py` is idempotent because of the SQL `INSERT OR REPLACE` strategy.

## Known limitations (future work)

1. **State code mismatch** (mentioned above) — 5–10% of true matches may be missed.
2. **GeoNames `altNames` not loaded** — historical_alias tier only catches dr5hn→dr5hn aliases. Loading GeoNames's alternateNames dump would unlock Mumbai↔Bombay, Edo↔Tokyo, Peking↔Beijing merges.
3. **GeoNames `elevation` not populated** — cities5000.txt doesn't include elevation; only cities1000.txt and alternate datasets do. The `elevation_m` column is currently NULL for all rows.
4. **Manual override update needed** — the 22 manual_override cities (M1 polygons) need their `display_name` to be re-evaluated.
