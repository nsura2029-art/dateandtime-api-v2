## Decision: Shadow mode (NOT promote)

**Why:** We have two sources of truth (dr5hn live, GeoNames staging) and
we want to compare them before flipping. Promoting now would:
- Lose 152,970 - 69,561 = 83,409 dr5hn cities (US/EU/IN skew)
- Replace dr5hn's 452K alt_names + 2.97M translations with 0
- Reset all M0-M10+ work that depends on dr5hn shape
- No rollback path without re-importing cities5000

**The cost of NOT promoting:** minor — we have a clean staging layer
that's queryable, auditable, and ready to promote when we want.

**The cost of promoting now:** high — we lose the existing product
context that took 10 milestones to build.

## What "shadow mode" means in practice

1. **dr5hn stays live** — `cities` table unchanged, all 152,970 cities
   served at `/api/v1/cities/*`
2. **GeoNames is queryable** — `/api/v1/staging/*` returns the 69,561
   GeoNames cities for inspection
3. **Both available for comparison** — same data, two sources, can diff
4. **A/B testing possible** — add a `?source=geonames` flag to search
   later (M11.1)
5. **Promote later** when confidence is high — script is ready

## How to compare

```bash
# Live dr5hn
curl "https://dt-api-v2-dev.nsura2029.workers.dev/api/v1/cities/search?q=Paris&limit=3"

# Staging GeoNames
curl "https://dt-api-v2-dev.nsura2029.workers.dev/api/v1/staging/cities?limit=100" \
  | jq '.cities[] | select(.name | test("Paris"; "i"))'
```

## How to promote later

When ready:

```bash
# 1. Run reconciliation again
python3 scripts/seed/reconcile_geonames.py

# 2. Run two-phase commit (asks for explicit yes)
bash scripts/seed/publish_geonames.sh
```

The script will:
- Validate D1 staging count = 69,561
- Create `cities_live_swap` from staging
- Show you the row count
- Wait for `yes` typed
- Atomic DROP+rename (live swap)
- Mark release as `published`

## What we'd lose vs gain by promoting

| Metric | Live (dr5hn) | Staging (GeoNames) | Net if swap |
|---|---:|---:|---|
| Total cities | 152,970 | 69,561 | **-83,409** (mostly US/EU/IN sub-15K) |
| Timezone quality (NULLs) | 22 unresolved | 0 unresolved | **+22** |
| Population quality (NULLs) | 35,546 NULL | 0 NULL | **+35,546** |
| Countries | 223 | 245 | **+22** (small island states) |
| Alt names (translations) | 451,000+ | 0 in our staging | **-451,000** |
| Translations (19 langs) | 2,965,561 | 0 in our staging | **-2,965,561** |
| Manual overrides (M0-M10) | 22 cities | 0 | **-22** |
| Data quality flags | 5,711 | 0 | **-5,711** |

**Verdict:** Promoting GeoNames alone loses too much. We need to:
1. Bring dr5hn's alt_names + translations forward AS-IS
2. Layer GeoNames on top (replace where better, add where missing)
3. THEN promote

This is "Option B" from the data platform design — 2-3 day task.

## Recommended next step (M11.1)

**Layer the two sources.** Plan:

1. Run dr5hn's `cities` table → `cities_live` as the base
2. For each GeoNames city:
   - If dr5hn has the same city (by name + state), keep dr5hn's record (it has the rich data)
   - If GeoNames has a city dr5hn doesn't, insert it with source='geonames'
3. Add 4 columns to `cities`: `source_id`, `release_id`, `source_population`, `source_timezone_confidence`
4. Bulk update dr5hn's TZ + population where GeoNames is more authoritative
5. Re-validate, re-test, re-stage as M11.1 release

Estimated: 2-3 days work.
