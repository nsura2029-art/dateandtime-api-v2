## What we had

After M11.2, the cities table looked like:

| Field | Coverage |
|---|---|
| `population` (existing) | 134,650 / 170,253 = 79.1% |
| `wiki_url` (new) | 117,711 / 170,253 = 69.1% |
| Wikidata population (in `wikidata_staging`) | 89,948 / 115,731 entities = 77.7% |

The gap: ~35,000 cities (mostly dr5hn origin) had a `wiki_data_id` but no population value, and Wikidata had population data for many of them.

## What we did

Built `scripts/seed/merge_wikidata_population.py` to apply Wikidata population values to the cities table.

**Strategy:** ONLY fill NULL populations. Never overwrite dr5hn's curated values.

**SQL pattern** (one statement, multiple rows via `CASE WHEN`):
```sql
UPDATE cities SET
  population = CASE wiki_data_id WHEN ? THEN ? WHEN ? THEN ? ... END,
  merge_run_id = ?, merged_at = ?
WHERE wiki_data_id IN (?, ?, ...) AND population IS NULL
```

12 Q-ids per call (36 binds, well under D1's 100-var limit), 16 parallel workers.

**Why CASE WHEN instead of multi-statement:**
- D1 HTTP API error: "params with multiple statements is not supported" (code 7400)
- CASE WHEN gives 1 statement = params OK = 9× faster than 1 UPDATE per call

**Time taken:** 8.2 min, 183 rows/s

## Known limitations

1. **Some Q-ids map to multiple cities** (typo variants, e.g. "Dibba Al Fujairah" / "Dibba Al-Fujairah" both reference Q3696182). The update fills all matching cities, which is correct behavior.
2. **The "none" source_primary 13,515 cities** lack a layer assignment. Many are dr5hn cities that didn't match GeoNames. These are still merge candidates for future data sources.
3. **Population freshness** — Wikidata population can be stale. dr5hn values are preserved when present (per the strategy).

## Gotcha learned (cross-project)

- **D1 HTTP API: params + multi-statement is rejected (code 7400).** Either use no params + literals (injection risk) or one statement per call. `CASE WHEN ... IN (...)` is the right pattern: one statement, multiple rows, params work.
