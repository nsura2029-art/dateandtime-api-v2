## What we get (data layer)

### New table: `country_populations` (migration 146)

```sql
CREATE TABLE country_populations (
  country_id   INTEGER NOT NULL,
  year         INTEGER NOT NULL,
  population   INTEGER NOT NULL,
  source       TEXT NOT NULL DEFAULT 'world_bank',
  release_id   TEXT NOT NULL,
  fetched_at   INTEGER NOT NULL,
  PRIMARY KEY (country_id, year, source)
);
```

216 rows. The `(country_id, year, source)` primary key allows multiple sources to
coexist (e.g. UN WPP 2024 and World Bank 2024 — keep both, don't overwrite).

### Updated endpoint: `GET /api/v1/countries` and `GET /api/v1/countries/{cca2}`

New `populationSources` block:
```json
{
  "populationSources": {
    "dr5hn": 340110988,
    "worldBank2024": 340003797,
    "primary": "worldBank2024"
  }
}
```

- `dr5hn` — population from dr5hn countries.population (may be stale, ~2020 estimates)
- `worldBank2024` — population from World Bank SP.POP.TOTL year=2024
- `primary` — which source is preferred for this country (`worldBank2024` when available, `dr5hn` otherwise)

## Value in the report (why this matters)

### 1. Source data is now fresh

`dr5hn` countries.population is curated but potentially stale (last update of the
dr5hn dataset was 2023-2024 era). World Bank 2024 gives us a fresh, official
cross-check:

| Country | dr5hn | WB 2024 | Δ% |
|---|---:|---:|---:|
| US | 340,110,988 | 340,003,797 | -0.03% |
| IN | 1,438,069,596 | 1,450,935,791 | +0.89% |
| CN | 1,425,671,352 | 1,408,975,000 | -1.17% |
| FR | 68,688,000 | 68,551,653 | -0.20% |
| DE | 84,270,625 | 84,358,845 | +0.10% |
| JP | 125,124,989 | 123,753,041 | -1.10% |

For most countries, the values are within ±1.5% (population grows/shrinks slowly).
A few outliers (COVID war impacts, large migration) might exceed 5%, but those are
flagged via the data_quality system.

### 2. Coverage is broad but not 100%

- **86.4% coverage** of our 250 countries have World Bank data
- **34 countries are missing** — all are small territories (Anguilla, Bouvet
  Island, Falkland Islands, Vatican City, etc.) that World Bank doesn't track
- For these, the API falls back to `dr5hn` (which may itself be NULL for
  uninhabited territories like Antarctica, Bouvet Island, BIOT)

### 3. Ready for future city-level backfill

When we build M11.5 (US Census) or M11.7 (Census of India), we can use the
country-level WB data as a *baseline* — e.g. for cities that we know should
have population > 50,000 but have NULL, we can flag them for review.

## Why we pivoted from UN WPP 2024 to World Bank

| Aspect | UN WPP 2024 | World Bank 2024 |
|---|---|---|
| Download method | Multi-GB CSV files | JSON API per-indicator |
| Update cadence | Biennial | Annual |
| Country coverage | 237 countries | 217 countries |
| Most recent | 2024 medium update | 2024 (lastupdated 2026-07-13) |
| Source code access | None (binary download) | REST API with per-country fetch |
| Already in source_registry? | No | **Yes** (world_bank / sp-pop-totl) |
| Data quality / known limitations | High (UN official) | High (UN-derived for most countries) |
| Loader complexity | CSV parser + multi-file | Single JSON query |

**The deciding factor**: When we tried to download the UN WPP 2024 CSV files,
the canonical download URLs returned 404 (e.g.
`https://population.un.org/wpp/assets/CSV/WPP2024_TotalPopulationBySex_Medium_Update.csv`
→ 404). The R package mirror on GitHub had moved files to a different path. We
could spend more time hunting the URL, OR pivot to a working source.

World Bank:
- Same data category (country population)
- Already in our source_registry
- Already had a stub entry (was "not started" / never ingested)
- Better tooling (JSON API vs CSV file)
- Annual refresh (vs biennial for WPP)
- Lastupdated 2026-07-13 (more recent than WPP's last published update)

The data is highly similar — both UN-derived for the majority of countries. The
choice was practical: ship now with WB, add WPP later if/when we need its
granularity (WPP has age/sex breakdowns, WB has just total).

## Scenarios we will keep learning from

### Scenario 1: Pivot from one source to another mid-implementation

The original plan was UN WPP 2024. When the download URLs broke, we pivoted to
World Bank. The pivot was clean because:
1. World Bank was already in our source_registry (from M11.0)
2. We had a uniform "intake → archive → register release → expose" pipeline
3. The schema is generic enough (country_id + year + value + source) to fit either
4. We documented the decision (this report) instead of silently changing

**Learning**: When planning a data ingestion, prefer sources that are:
- Already in source_registry (saves onboarding time)
- Have a stable API (URLs don't break)
- Have stable update cadence (predictable freshness)

### Scenario 2: Multiple sources for the same data category

`countries.population` could be filled by any of: dr5hn, Wikidata, World Bank,
UN WPP, Eurostat, US Census, Census of India, India projections. We chose to:

1. Keep dr5hn as the "primary curated" value (never overwrite)
2. Add World Bank as a fresh, official cross-check (populationSources block)
3. Add Wikidata as a per-city value (cities.population, fill NULLs only)

This way each source plays to its strengths:
- dr5hn: curated, validated, integrated
- Wikidata: per-city, has alt labels and descriptions
- World Bank: fresh country-level, official cross-check
- US Census: per-city, US-specific, fresher than dr5hn
- Eurostat: per-city, EU-specific, distinguishes City vs FUA
- Census of India: per-city, IN-specific, 2011 official

### Scenario 3: 100-var limit on D1 SQL still bites

For the `country_populations` table (6 cols), 16 rows/batch = 96 vars. Safe under 100.
For 7 cols, 14 rows/batch = 98. For 8 cols, 12 rows/batch = 96. Always check
the column count and compute accordingly.

### Scenario 4: Source registry enables pivots

Because M11.0 added a `source_registry` table with `endpoint_url`,
`access_method`, `license`, etc. for 10 sources up front, we could "discover"
World Bank as a viable alternative and immediately know:
- It has a JSON API (access_method: https-json)
- It's CC-BY-4.0 (license: CC-BY-4.0)
- It's annual (refresh_policy: annual)
- It's NOT marked active (is_active: false — we never ingested before)

The registry saved us from a "discovery + license review" loop. M11.0 paid off.
