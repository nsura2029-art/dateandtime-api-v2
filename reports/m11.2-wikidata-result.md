# M11.2 Wikidata Report — 117K cities get Wikipedia URLs

**Date:** 2026-08-02
**Branch:** `feature/m11.2-wikidata` (merged to develop)
**Status:** ✅ APPLIED TO D1
**Live URL:** https://dt-api-v2-dev.nsura2029.workers.dev

## TL;DR

Loaded 115,731 Wikidata entities for our 118,731 cities (those with a
`wiki_data_id`) into D1 `wikidata_staging` via SPARQL POST queries. Applied
the merge to populate `cities.wiki_url` for 117,711 cities (69% of all
cities). The API now exposes `wikiUrl` on `/cities/{id}` and
`/cities/search` responses.

## What we had (input)

| Source | Count | Notes |
|---|---:|---|
| dr5hn cities with `wiki_data_id` (Q-id) | 118,731 | 87% of dr5hn cities |
| Wikidata Query Service (SPARQL) | unlimited | Public, CC0 |
| Endpoint | https://query.wikidata.org/sparql | Rate-limited, 5 req/sec |

## What we did

1. **Migration 143** (already shipped) — `wikidata_staging` table + `cities.wiki_url` column
2. **Wikidata SPARQL fetch** (1,000 Q-ids per POST request, 1 worker, 15.4 min)
   - SPARQL returns label, altLabel, Wikipedia URL, population per Q-id
   - Used POST because GET fails with 414 URI Too Long at 5K+ Q-ids
3. **Parallel HTTP API load** (16 workers, 11 rows/batch, 99 vars/batch, ~50 min)
4. **Merge to cities** (parallel HTTP API, 7 min, 117K updates)
5. **Source release registered** — `wikidata-entities-2026-08-02`, status='raw-stored'
6. **API updated** to expose `wikiUrl` on detail and search responses

## Value delivered

1. **Wikipedia URL for 117,711 cities (69%)** — apps can now link to Wikipedia for any major city without an additional API call
2. **117,731 English labels** from Wikidata (often more accurate than dr5hn's labels for non-English-origin names)
3. **89,948 population values** — additional data point for cities where dr5hn had NULL
4. **Future foundation** for cross-source merge:
   - Wikidata Q-id (already in `wiki_data_id`) is a stable identifier
   - Wikipedia URL provides a "deep link" for end users
   - Population values can be cross-referenced with UN WPP (M11.4) and World Bank (M11.8)

## What we learned

1. **SPARQL POST is required** — GET with 5K Q-ids returns 414 URI Too Long. Use POST with `Content-Type: application/sparql-query` and the SPARQL in the body.

2. **Wikidata throttles aggressively** — ~0.2 batches/sec at 1K Q-ids per request. With 1 worker, 119 batches = 15.4 min. Multiple workers get 429 rate-limited.

3. **JSON parse errors from control characters** — some Wikidata literal values contain `\u0001`-style control chars. Strip them with regex `[\x00-\x08\x0b-\x0c\x0e-\x1f]` before parsing.

4. **D1 HTTP API parallelism is the way** — 117K UPDATE statements applied in 7 minutes via 16 parallel workers. Wrangler per-statement would have taken 10+ hours.

5. **21% of Q-ids have no Wikipedia article** — these are valid Wikidata entities (e.g. tiny villages) but no encyclopedia entry. Still useful for the English label and population.

6. **GeoNames-only cities (17,283) have no wiki_url** — because they don't have a Q-id in dr5hn. To get them a Wikipedia URL, we'd need a separate Wikidata query by name+coords (much more complex). Deferred.

## Known limitations

1. **17,283 GeoNames-only cities don't have wiki_url** — needs a separate name+coords→Wikidata query. Not done.

2. **30,620 dr5hn cities with wiki_data_id but no wiki_url** — these have a Q-id but Wikidata said "no Wikipedia article". This is correct behavior (no article = no URL).

3. **Alt labels from Wikidata are not yet in our search strategy** — could be added as a future enhancement. The data is in `wikidata_staging.alt_labels_json`.

4. **Population values are not yet applied to cities** — would need a separate merge step. The data is in `wikidata_staging.wikidata_population`.
