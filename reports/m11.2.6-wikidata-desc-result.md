## What we have in the data

### Wikidata staging layer (M11.2)

We already have the Wikidata layer from M11.2:
- `wikidata_staging` table: 115,731 rows
- Columns: `staging_id, release_id, qid, english_label, alt_labels_json, wikipedia_url, wikidata_population, retrieved_at`
- Cities table has `wiki_data_id` for 148,331 cities (87% of 170K)

### Coverage gap

- 148,331 cities with `wiki_data_id` (87% of 170K)
- 115,731 Wikidata rows fetched in M11.2
- **3,618 cities have `wiki_data_id` but no wikidata_staging row** (the M11.2 ingestion didn't fetch every QID — it stopped at the most populous 115K)
- So 144,713 cities have full wikidata data, 3,618 have an empty block, 21,922 have no wikidata

## What we get (API changes)

### New `wikidata` block in `/api/v1/cities/{id}` response

```json
{
  "wikidata": {
    "label": "Tokyo",
    "altLabels": ["Yedo", "Tōkyō-to", "Tôkyô-to", "Tokyo-to", "Tokyo Metropolitan prefecture"],
    "description": "Tokyo (also known as Yedo)"
  }
}
```

Three cases for the `wikidata` field:

| Case | Field value | Meaning |
|------|-------------|---------|
| 1. City has no `wiki_data_id` | `wikidata: null` (absent) | 21,922 cities — small GeoNames-only or no Wikidata concept |
| 2. City has `wiki_data_id` but no staging row | `wikidata: { label: null, altLabels: [], description: null }` | 3,618 cities — QID linked but not yet fetched |
| 3. City has full data | `wikidata: { label, altLabels: [...], description: "Label (also known as First Alt)" }` | 144,713 cities (85%) |

### Description format

`description = "Label (also known as First Alt)"` when first alt label exists
`description = "Label"` when no alt labels
`description = null` when no label (only relevant for case 2)

### Constraints

- `altLabels` limited to first 5 entries (keeps response size reasonable)
- `label` is the English canonical name from Wikidata (may differ from dr5hn city name)
- `altLabels` excludes the canonical name (avoids duplication)

## Value in the report (why this matters)

### 1. SEO and discoverability

City pages can now include a one-line description in their `<meta description>`
tag or as a subtitle. The format `"Tokyo (also known as Yedo)"` immediately
tells users (and search engines) what the city is and its most famous alt name.

Without this, city pages have only the city name. With it, they have:
- **Tokyo** | (also known as Yedo)
- **Paris** | (also known as City of Love)
- **New York City** | (also known as NYC)

### 2. Cross-language disambiguation

Some cities have multiple names across languages. The description is a
"default English" representation:
- Köln (German) → label: "Cologne" (Wikidata English canonical)
- Firenze (Italian) → label: "Florence"
- München (German) → label: "Munich"

The dr5hn `cities.name` field is the local-script name. The Wikidata `label`
is the English canonical. Having both helps international users.

### 3. Ready for content generation

The alt labels can power:
- Tooltip on hover: "Tokyo (also known as Yedo, Tōkyō-to, ...)"
- Search-as-you-type autocomplete: typing "yedo" matches via Strategy A3
- "Common nicknames" section on city pages
- Translation memory (Wikidata is multilingual via Q-ids)

### 4. Foundation for M11.2.7+ (richer descriptions)

Future work could:
- Add Wikidata "instance of" (P31) — distinguish "city" from "town" from "village"
- Add "located in" (P17) for country, P131 for admin region
- Add population from Wikidata (already in wikidata_staging.wikidata_population)
- Add inception date (when founded)
- Add elevation from Wikidata

## Scenarios we will keep learning from

### Scenario 1: Coverage gap (148K → 115K)

The M11.2 Wikidata ingestion fetched 115,731 Q-ids. We have 148,331 cities
with `wiki_data_id`. That's a 32,600 gap.

**Why the gap exists**: M11.2 prioritized populous cities. The Q-ids that
weren't fetched tend to be smaller/less-known places. Many of these are in
the GeoNames-only 17K cities or in dr5hn's secondary city list.

**What we could do**:
1. **Re-run the Wikidata SPARQL ingestion** for the missing 32,600 Q-ids
2. **Ingest by name+coords** as a fallback (complex, deferred)
3. **Accept the gap** — 3,618 / 170K = 2.1% of cities affected. Not a big deal.

For now, we accept the gap. The empty block tells clients "data should exist
but we don't have it yet" so they can request enrichment later.

### Scenario 2: Description is just the name + first alt

This is the simple "use english_label + first alt label" approach the user
asked for. It's not as rich as a proper description like "Tokyo is the
capital of Japan and the most populous metropolitan area in the world."

**Trade-off**:
- Simple: just use what we have (english_label + first alt)
- Rich: requires more Wikidata properties (P31, P17, P131) which we haven't
  fetched yet

For M11.2.6 we chose simple. Future M11.2.7+ can layer in richer descriptions
when we ingest the additional Wikidata properties.

### Scenario 3: Adding a query to a hot endpoint

The `/cities/{id}` endpoint is one of the hottest endpoints. It already does
5 queries (city+joins, place_names, postcodes, translations). Adding a 6th
query (wikidata) adds ~20-30ms.

**Mitigation**:
- The wikidata query is O(1) — `WHERE qid = ?` with a primary key lookup
- Only fires for cities with `wiki_data_id` (~85% of cities)
- No additional latency for cities without wikidata

**Trade-off**:
- Pro: rich data, single endpoint call
- Con: +20-30ms per detail call

For 85% of cities, the user gets the description. For the other 15%, no
extra latency. Acceptable.

### Scenario 4: Returning null vs empty block

We chose to return an empty block (`{ label: null, altLabels: [], description: null }`)
when the city has `wiki_data_id` but no staging row. The alternative is to
return `null` for both cases.

**Why we did it this way**:
- Clients can distinguish "no wikidata" (null/absent) from "wikidata missing" (empty block)
- The empty block still has the structure, so clients don't need null-checks on every field
- It's a hint to "we know this city has wikidata, but we haven't fetched it yet"

The trade-off: response size is larger for the 3,618 affected cities (they
get an empty object instead of nothing). Not significant.
