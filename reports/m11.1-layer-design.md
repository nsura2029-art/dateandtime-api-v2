## What we have → What we get → Value

**What we have:**
- dr5hn cities with `name`, `ascii_name`, `native` columns
- GeoNames cities with similar columns but different conventions
- 451K alt_names from dr5hn (handles historical renames like Bombay→Mumbai)
- 2.97M translations in 19 languages

**What we get:**
- A single `cities` table with both sources' data, no duplication
- `display_name` that looks correct in UI (no "St." abbreviation)
- `search_name` that indexes clean (no diacritics, all lowercase)
- `geonames_id` so we can join back to GeoNames for future releases
- Better timezone + population where GeoNames is authoritative

**Value:**
- UI shows "Saint Petersburg" instead of "St. Petersburg" (cleaner)
- Search matches "São Paulo" / "Sao Paulo" / "SAO PAULO" (better recall)
- Sub-15K villages like Vinjanampadu finally return results
- Each row has a `source` so we can audit which data came from where

## Intelligent merge strategy

### Step 1: Match dr5hn ↔ GeoNames

For each GeoNames city, find the matching dr5hn record using this priority:

1. **Exact name + admin1 match** (95% of cases)
   - `LOWER(dr5hn.name) = LOWER(geonames.name)` AND `dr5hn.state_id = geonames.admin1_code`

2. **Historical name match** (Bombay↔Mumbai, etc.)
   - Check dr5hn's `place_names` table for an alias to GeoNames' canonical name
   - Example: dr5hn has city "Mumbai" + place_name "Bombay" → matches GeoNames' "Mumbai" (because GeoNames also has "Bombay" as alt_name)

3. **Fuzzy match by population + coordinates** (rare)
   - If same name in same country, different admin1 (boundary discrepancies)
   - If names differ but population + coords within 0.5°/10%

### Step 2: Per-city decision matrix

| Case | dr5hn action | GeoNames contribution |
|---|---|---|
| Match via Rule 1 | UPDATE geonames_id, elevation, optionally pop/tz | "merged" |
| Match via Rule 2 (historical) | UPDATE geonames_id, set `was_renamed=1` | "merged_via_alias" |
| No match (dr5hn has it, GeoNames doesn't) | Mark `geonames_id=NULL`, keep dr5hn | "dr5hn_only" |
| GeoNames only (no dr5hn match) | INSERT with `source='geonames'` | "geonames_only" |

### Step 3: Field-level arbitration

When both sources have data, who's authoritative?

| Field | Authoritative source | Reason |
|---|---|---|
| `name` (canonical) | dr5hn | has translations + alt_names attached |
| `display_name` | dr5hn + smart expansion | rules-based, computed |
| `short_name` | GeoNames if available, else dr5hn | GeoNames has better short forms |
| `timezone` | GeoNames (if confidence > dr5hn) | GeoNames polygon-verified for 2,983 cities |
| `population` | GeoNames (always) | GeoNames has 0 NULLs vs dr5hn's 35,546 |
| `latitude/longitude` | GeoNames (if more decimal places) | GeoNames typically more precise |
| `elevation_m` | GeoNames (only) | dr5hn doesn't have it |
| `country_id`, `state_id` | dr5hn | already validated via FK |
| `alt_names`, `translations` | dr5hn | GeoNames doesn't have these |
| `manual_override` | dr5hn | preserves our 22 manual edits |
| `tier` | dr5hn | 70 tier1, 3,511 tier2 curated |

### Step 4: Provenance tracking

Each row will have:
- `source_primary` — 'dr5hn' or 'geonames' (which source provided the canonical record)
- `source_merged_with` — 'geonames' | 'dr5hn' | NULL (which source we merged in)
- `merge_method` — 'exact' | 'historical_alias' | 'fuzzy' | NULL
- `merge_run_id` — UUID of this M11.1 run (so we can roll back)

This is "row-level provenance" — a D1 platform principle from the data platform design.

## The match algorithm in code (sketch)

```python
def match(dr5hn_row, geonames_row):
    # Rule 1: exact match
    if (dr5hn_row.name.lower() == geonames_row.name.lower()
        and dr5hn_row.state_id == geonames_row.admin1_code):
        return ('exact', dr5hn_row.id)

    # Rule 2: historical alias
    alias = db.execute("""
        SELECT canonical_place_id FROM place_names
        WHERE LOWER(name) = ? AND place_type = 'city'
    """, geonames_row.name.lower()).first()
    if alias and alias.canonical_place_id == dr5hn_row.id:
        return ('historical_alias', dr5hn_row.id)

    # Rule 3: fuzzy (population + coords proximity)
    if (geonames_row.population and dr5hn_row.population
        and abs(dr5hn_row.population - geonames_row.population) / dr5hn_row.population < 0.5
        and haversine_km(dr5hn_row.lat, dr5hn_row.lon,
                          geonames_row.lat, geonames_row.lon) < 50):
        return ('fuzzy', dr5hn_row.id)

    return (None, None)  # no match
```

## Expected outcomes (predicted)

Based on naming patterns:
- ~85% match via Rule 1 (exact)
- ~5% match via Rule 2 (historical renames)
- ~5% match via Rule 3 (fuzzy)
- ~5% GeoNames-only (sub-15K villages)
- dr5hn loses ~5-10% that GeoNames doesn't have (rare, mostly sub-15K that GeoNames has but dr5hn doesn't)

Net: cities table grows from 152,970 to maybe 170,000-180,000.

## Scenarios we'll learn

1. **Display name conflicts** — "São Paulo" vs "Sao Paulo" (with vs without diacritic). Pick one.
2. **Population disagreement** — when GeoNames and dr5hn differ by >20%, which wins? (Proposal: GeoNames for current, dr5hn for historical context)
3. **State code mismatches** — dr5hn uses 2-letter US codes (CA), GeoNames uses FIPS codes (06). Need a mapping table.
4. **Timezone upgrades** — dr5hn "default" GeoNames "polygon-verified". Promote polygon-verified when both available.

## Risk + rollback

- Migration adds columns, doesn't drop anything — safe to revert
- Merge writes new columns (`geonames_id`, `display_name`, etc.) — overwrites are idempotent
- Rollback = clear those columns + delete the inserted GeoNames-only cities
- We keep `cities_staging` intact as a safety net until M11.1 is validated
