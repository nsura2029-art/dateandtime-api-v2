# M11.2.5: Wikidata alt_labels to Search — Result Report

**Date:** 2026-08-02
**Status:** ✅ APPLIED — new search strategy A3 live
**Branch:** `feature/m11.2.5-wikidata-altlabels` (ready to merge to develop)

## What we had

`wikidata_staging.alt_labels_json` held 91,500+ alt labels for 45,517 entities (e.g. Tokyo had 14 alt labels: "Yedo", "Jedo", "Edo", "Tokei", etc.). But this rich data was only in the staging table — not searchable via the API.

For queries like "yedo", "big smoke", "lundenwic", the existing search strategies returned 0 results (or wrong cities), so users couldn't find Tokyo, London, etc. by their historic or colloquial names.

## What we did

### New search strategy A3 (src/routes/cities.ts)

A new fallback strategy in `/api/v1/cities/search` runs after Strategies A (search_name LIKE) and A2 (alt_names_staging), but before Strategy B (place_names). It catches alt labels that the earlier strategies miss.

**SQL pattern:**
```sql
SELECT ... , 1 as from_wikidata_alt
FROM wikidata_staging ws
JOIN cities ci ON ci.wiki_data_id = ws.qid
WHERE LOWER(ws.alt_labels_json) LIKE LOWER(?)
  AND ws.release_id = ?
  AND ci.is_active = 1
```

**Pattern construction:**
- Single-word query: `%"qNorm"%` (e.g. `%"yedo"%`)
- Multi-word query: `%"qLower"%` (e.g. `%"big smoke"%`) — uses full string with spaces

**Match type:** Added `"alt_label"` to the matchType enum. When a result comes from Strategy A3, matchType is set to `"alt_label"` so clients can distinguish alt-label matches from regular exact/prefix/fuzzy matches.

### Tests (tests/m11.2.5-wikidata-altlabels.test.ts)

15 tests covering:
- Historic names (Yedo/Jedo/Tokei → Tokyo, Lundenwic → London)
- Colloquial names (Big Smoke → London, Puritan City → Boston)
- Case insensitivity (yedo/Yedo/YEDO all work)
- Strategy priority (Strategy A still wins for prefix matches)
- Performance (under 3 seconds)
- Schema (matchType enum includes "alt_label")

## Strategy execution order (M11.2.5)

1. **FTS5** (place_names_fts) — fastest, highest quality, prefix + exact
2. **Strategy A** (cities.search_name LIKE) — M11.1 layer column
3. **Strategy A2** (alt_names_staging) — GeoNames alt names, M11.1.5
4. **Strategy A3** (wikidata_staging.alt_labels_json) — Wikidata alt names, **M11.2.5 (NEW)**
5. **Strategy B** (place_names.normalized_name) — dr5hn legacy fallback

Each strategy only runs if earlier ones returned 0 results. So A3 only kicks in for queries where FTS5/A/A2 don't find a match.

## Gotchas hit (cross-project)

1. **Multi-word alt labels** (e.g. "big smoke", "puritan city") need full `qLower` with spaces. Single-word queries use `qNorm` (no spaces). The pattern is `qLower.includes(" ") ? '%"${qLower}"%' : '%"${qNorm}"%'`.

2. **FTS5 often matches before A3**: For "londinium", FTS5's prefix match `londinium*` finds the alt name in place_names, so A3 never runs. This is correct — FTS5 is the fastest and highest quality match. A3 is a fallback for queries FTS5 misses.

3. **The `from_wikidata_alt` SQL field is used to set matchType**: Without that column, the dedup step in search results can't tell if a row came from A3 vs other strategies. The 4th strategy's result wins via the `fts_rank < existing.fts_rank` tie-breaker, but we use the explicit `from_wikidata_alt` flag for clarity.

4. **Hono Context doesn't preserve extra properties** (e.g. `(c as any).__searchDebug` is null at response time). For module-level debug, use a `let debugLastX: any = null` variable. (This is how I debugged why A3 wasn't running for "londinium" — turned out FTS5 was matching it.)
